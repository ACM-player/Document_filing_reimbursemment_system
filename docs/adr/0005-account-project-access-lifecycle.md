# ADR-0005：账号与项目授权生命周期

- 状态：接受
- 日期：2026-08-10

## 背景

Phase 1 的账号状态会同步 Django `is_active`，但原后台直接保存状态，不会结束 Phase 2 的项目成员关系
或访问申请。若把临时禁用与永久离组混为一谈，恢复账号可能意外恢复旧授权；若成员页移除、申请撤销和
到期各自改写不同记录，则申请状态、成员状态和审计也会分叉。

## 决策

账号状态只通过账号服务按以下状态机变更：

```text
ACTIVE <-> DISABLED
ACTIVE -> DEPARTED -> ARCHIVED
DISABLED -> DEPARTED
```

同状态操作幂等。`DEPARTED` 和 `ARCHIVED` 是不可逆终态，不能通过受支持服务恢复为 ACTIVE 或
DISABLED；`ACTIVE -> ARCHIVED` 也不能跳过离组。

`DISABLED` 只暂停认证和权限行使，不结束 Membership，也不取消 PENDING / APPROVED 申请。恢复
ACTIVE 时先归一化已经自然到期的申请授权，仍有效的原授权使用同一历史记录恢复行使。

进入 `DEPARTED` 或 `ARCHIVED` 时，在账号状态和审计的同一数据库事务中：

- PENDING 申请变为 CANCELLED；
- APPROVED 申请通过一对一来源关系撤销，并结束其精确 Membership；
- 其余活动 DIRECT Membership 全部结束；
- REJECTED、CANCELLED、EXPIRED 和已经结束的历史记录保持不变。

审批人的 `reviewed_by`、`reviewed_at` 和 `review_note` 只描述原审批，不被取消、撤销、到期或离组
覆盖。关闭动作的操作者、原因和时间写入追加式 AuditLog。系统不硬删除或改写申请授权的来源、角色和
原到期时间。

任何未软删除项目（包括 ARCHIVED 项目）的规范 PI 在离组或归档账号前必须先显式转移负责人；系统不
自动选择继任者。软删除项目不阻断账号终止，但其历史授权会被结束；未来若增加恢复软删除项目的能力，
必须在恢复前重新指定 ACTIVE PI。

成员页移除申请产生的 VIEWER 时复用申请撤销路径；移除 DIRECT 成员只结束成员关系。高风险审计写入
失败时，账号、申请、Membership 和已经写入的审计一起回滚。

到期采用三层保证：权限查询立即忽略超过 `expires_at` 的授权；展示项目授权状态的页面执行项目级归一
化；幂等管理命令 `expire_project_access` 持久化无人访问项目的 EXPIRED 状态与审计。Phase 2 不引入
进程内调度器；部署外部定时任务前，只能声明权限即时失效和人工命令可归一化，不能声明无人访问时状态
会按墙钟持续自动落库。

账号永久终止当前不静默删除 Django Group。受支持状态机禁止终态重新激活；系统角色是否在离组时移除
属于独立授权政策，后续若调整必须逐条审计并补重新授权流程。

## 未采用方案

- 把 DISABLED 当作离组：会使临时停用不可逆地丢失仍有效的项目授权；
- 在 `User.save()` signal 中级联项目清理：缺少可靠 actor 和请求上下文，也会让 fixture、migration 和
  低层保存产生隐式业务副作用；
- 用 Django 进程内线程或定时器处理到期：开发重载、多进程和部署重启下不能保证唯一可靠执行；
- 自动为离组 PI 选择继任者：负责人选择属于业务决定，不能由系统猜测。

## 后果

- 临时停用和永久离组具有不同、可测试的授权语义；
- 低层绕过状态服务属于不受支持的写路径，但已经结束的 RESTRICTED Membership 不会因此复活；
- 项目授权关闭与账号状态审计具备事务一致性；
- 生产持续到期归一化仍依赖部署阶段配置并验证外部调度器；
- 授权入口统一采用 User → Project → AccessRequest → Membership 行锁顺序；重复成员设置、移除、
  取消和撤销具有幂等语义。离组与直接授权/审批、PI 转移与旧 PI 离组、移除与撤销/到期的首批
  PostgreSQL 真实并发回归已经覆盖；未来新增授权写路径仍必须沿用该锁序并增加对应并发测试。
